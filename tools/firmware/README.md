# FCPLCn — Future City PLC Next

Инструменты для сборки прошивки, локального веб-интерфейса и тестов на Mac с Apple Silicon.

Название продукта — **FCPLCn**, полное название — **Future City PLC Next**. Канонические значения хранятся в `config/product.json` и используются прошивкой и веб-интерфейсом. Видимое написание всегда `FCPLCn`; технические идентификаторы в нижнем регистре — `fcplcn`. При реализации новых функций это имя используется также в сведениях об устройстве, API, hostname, MQTT/discovery и именах выпусков.

Связь устройств, автономность, настройка и облачная часть описаны в [концепции архитектуры](../../docs/architecture/CONCEPT.md).

Текущая структура: основной TypeScript-сервис и MQTT-брокер размещаются на Linux мини-ПК; PLC работают с ним по MQTT в локальной сети, а связь с облаком выполняет только мини-ПК. Термоконтроль, локальные защиты и другие автономные контуры постоянно выполняются в C++ на PLC и продолжают работу при потере мини-ПК или брокера.

Базовая прошивка контроллера с Wi-Fi AP/STA, Ethernet W5500, авторизацией, RTC/NTP, аппаратными профилями, реле/входами MCP23017, диагностикой I²C и Linux MQTT находится в [firmware/base](../../firmware/base/README.md). Вкладка «Контроллеры» содержит автономные «Розетки», «Свет», «Метео», «Термостат», «Охрана», «Баки» и «Полив»: веб/MQTT, кнопки с учётом полярности платы, сохранение состояний, датчики DHT22/DS18B20 и автономный нагрев/охлаждение с гистерезисом 1°…20°, индивидуальным выключателем и необязательной кнопкой входа. Выключатель термостата доступен через веб и MQTT, сохраняется на PLC. OneWire поддерживает несколько датчиков на порту с выбором по ROM, реле и цифровые входы назначаются эксклюзивно; источники «Метео» могут быть общими для нескольких термостатов. В «Системе» доступны имя устройства и полная JSON-конфигурация v10 со всеми контроллерами для переноса на PLC с совпадающим профилем; старые v1/v2/v3/v4/v5/v6/v7/v8/v9 поддерживаются. Проверка: `tools/firmware/test-base-backup`. Проверки логики: `tools/firmware/test-base-sockets`, сенсорных протоколов: `tools/firmware/test-base-meteo`; браузера: `tools/firmware/test-base-ui`. Сборка: `tools/firmware/build-base`; готовые файлы: `firmware/base/dist/`. Симулятор без контроллера: `tools/firmware/preview-base`, адрес `http://127.0.0.1:4174`.

## Состояния контроллеров во FRAM и EEPROM

| Профиль             | Микросхема          | Ёмкость | I²C               |
| ------------------- | ------------------- | ------- | ----------------- |
| `fcplcn-161608-1v0` | FRAM FM24CL64B-GTR  | 8 КиБ   | `0x50`, SDA4/SCL5 |
| `fcplc-080806-3v1`  | EEPROM 24LC512-I/SM | 64 КиБ  | `0x50`, SDA2/SCL1 |

Тип памяти задаёт аппаратный профиль. Общий драйвер выбирает FRAM или EEPROM;
24LC512 учитывает границы страниц 128 байт, ожидает завершения программирования,
проверяет запись чтением и пропускает совпадающие блоки. В карточке памяти сервисного
веба тип и модель меняются вместе с активным профилем. EEPROM имеет ограниченный
ресурс записи, поэтому измерения и автоматические переключения регуляторов остаются в RAM.

Настройки и учётная запись остаются в общем NVS-блобе `fcplcn_state/state`.
Состояния розеток/света, индивидуальные разрешения термостатов, баков и правил полива, режим/тревога охраны
сохраняются во внешней памяти без перезаписи NVS при каждом переключении.
Два слота по 256 байт занимают первые 512 байт; оставшаяся ёмкость не занята журналом.
Журнал проверяет CRC, завершение записи и ключ конкретной конфигурации.
При недоступной/повреждённой памяти обычные выходы стартуют выключенными,
а включённая охрана — с тревогой и диагностикой; устаревшее ON из Flash не восстанавливается.
Прежний формат один раз мигрирует после успешной подготовки постоянной памяти.
Внутренняя секция — `FCCTRL11`, переносимый JSON — **v10** с актуальными состояниями.
При импорте внешняя память подготавливается перед NVS; неуспешная запись сохраняет
прежнюю конфигурацию и её слот состояний.

Проверки на компьютере:

```sh
tools/firmware/test-base-board-profiles # Начальные профили, алиасы и упаковка образов.
tools/firmware/test-base-state-memory  # Выбор FRAM/EEPROM, страницы, ожидание готовности и ошибки.
tools/firmware/test-base-hardware-io   # Драйвер, адресация, границы, ошибки и общий I²C.
tools/firmware/test-base-fram-journal  # CRC, слоты, прерывание записи и ключ конфигурации.
tools/firmware/test-base-sockets      # Восстановление состояний и миграция контроллеров.
tools/firmware/test-base-backup       # Актуальный экспорт и перенос NVS + внешняя память.
```

На плате дополнительно проверяются наличие `0x50` и восстановление состояний
после полного отключения питания. Сборка и тесты на ПК не заменяют эту проверку.

## Сборка для выбранной платы

Из корня репозитория:

```sh
# Современная FCPLCN-161608-1v0 с FRAM:
tools/firmware/build-base
# Предыдущая FCPLC-080806-3v1 с EEPROM:
FCPLCN_BOARD_PROFILE=fcplc-080806-3v1 tools/firmware/build-base
```

Для современной платы сохранены `~/esp/build/fcplcn/base/` и `firmware/base/dist/`.
Для предыдущей используются `~/esp/build/fcplcn/base-fcplc-080806-3v1/` и
`firmware/base/dist/fcplc-080806-3v1/`. В пакете есть `firmware-profile.json`;
упаковщик сверяет начальную модель с CMake cache и не смешивает разные модели
в одном каталоге выпуска. Пути переопределяются `FCPLCN_BASE_BUILD_DIR` и `FCPLCN_BASE_DIST_DIR`.

Начальный профиль применяется при отсутствии сохранённой модели. Сохранённый
`hardware.boardId` имеет приоритет и применяется после чтения настроек;
профиль меняется через «Система → Модель платы» с перезагрузкой.
GPIO назначаются только после проверки и активации профиля.

Распиновка старой платы, обратная полярность её входов и обязательное исправление
SDA/SCL и WP EEPROM: [FCPLC-080806-3v1](../../docs/hardware/FCPLC-080806-3v1.md).

## Инструменты

- `tools/firmware/test-base-management` — приватная MQTT-настройка: фрагменты,
  сроки, повторы, маршруты, конфигурации, права портов и резервная копия.
- `tools/firmware/test-base-ota` — обновление приложения: неактивный раздел,
  ограниченные фрагменты, SHA-256, отмена, сроки, ошибки flash и выбор загрузки.
- ESP-IDF: стабильный тег `v6.1`, SDK в `~/esp/esp-idf-v6.1`, инструменты и отдельное Python-окружение в `~/.espressif`.
- Python 3.12, CMake, Ninja, ccache, dfu-util — Homebrew.
- Node.js 24 LTS и npm — Homebrew; зависимости веб-стенда закреплены в `web-smoke/package-lock.json`.
- Mosquitto — локальный MQTT-брокер. Тест запускает временный экземпляр только на `127.0.0.1`; постоянный сервис не требуется.
- pytest и paho-mqtt — отдельное окружение `integration/.venv`, версии в `integration/requirements.lock.txt`.
- esptool для ручного управления: `../esp/esptool`; порты: `../esp/ports`.

Глобальные настройки оболочки менять не нужно: команды запуска сами подключают нужное окружение. Путь SDK можно переопределить переменной `ESP_IDF_SDK_DIR`.

## Проверочная прошивка

`esp32s3-smoke` проверяет возможность собрать проект для ESP32-S3 и подключить официальные компоненты W5500 и MQTT, а также UART и HTTP-сервер ESP-IDF. Версии управляемых компонентов записаны в `esp32s3-smoke/dependencies.lock`.

Настройки N16R8: Quad Flash 16 МиБ при 80 МГц, Octal PSRAM 8 МиБ при 80 МГц, консоль USB Serial/JTAG. Octal Flash не включается.

В `esptool image-info` заголовок образа показывает DIO: ESP-IDF намеренно записывает этот режим для начальной загрузки, а затем включает QIO согласно `CONFIG_ESPTOOLPY_FLASHMODE_QIO=y`.

Результаты сборки хранятся в `~/esp/build/fcplcn/esp32s3-smoke/`. GCC из ESP-IDF 6.1 некорректно читает specs-файл, если каталог сборки содержит кириллицу, поэтому используется отдельный путь ASCII. Путь можно изменить переменной `ESP_SMOKE_BUILD_DIR`.

После сборки в этом каталоге находятся:

- `FCPLCn.bin` — приложение;
- `bootloader/bootloader.bin` — загрузчик;
- `partition_table/partition-table.bin` — таблица разделов;
- `FCPLCn-full.bin` — объединённый образ для первой USB-прошивки;
- `flasher_args.json`, ELF и map — параметры прошивки и данные для отладки.

При запуске на плате проверочная прошивка печатает сведения о чипе, проверяет объём Flash/PSRAM и короткий участок PSRAM. Управление реле, настройка сети, обмен RS485 и продуктовый веб-интерфейс в неё не входят. Тесты на компьютере проверяют инструменты и локальные протоколы; физическую работу периферии нужно проверять на плате.

## Сборка и прошивка будущего проекта

```sh
tools/firmware/idf -C /absolute/path/to/project -B /Users/sergey/esp/build/fcplcn/app build
tools/firmware/idf -C /absolute/path/to/project -B /Users/sergey/esp/build/fcplcn/app merge-bin -o FCPLCn-full.bin
tools/firmware/idf -C /absolute/path/to/project -B /Users/sergey/esp/build/fcplcn/app -p /dev/cu.usbmodem... flash
```

Команда `build-smoke` ничего не записывает в контроллер. Текущая проверочная прошивка использует заводской раздел без OTA; OTA-разделы добавляются в рабочем проекте.

Для платы `FCPLCN-161608-1v0` при прошивке через сервисный USB-C J2 требуется штатное питание 12 В: USB не питает плату. См. [инструкцию сборки платы](../../../fcplcn-boards/FCPLCN-161608-1v0/ASSEMBLY.md).

## Оформление исходников и Doxygen

Проверки отказоустойчивости и транспорта:

```sh
tools/firmware/test-base-runtime       # Прогресс задач, независимость и переполнение времени.
tools/firmware/test-base-telemetry     # Изменения, свежесть, retry/reconnect и большой каталог.
tools/firmware/test-base-static-cache  # Gzip/identity, ETag, версия ресурсов.
```

Стиль FCPLCn основан на [рекомендациях Espressif](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/contribute/style-guide.html) и закреплён в [`.clang-format`](../../.clang-format). Отступ C++ — четыре пробела, скобка функции на новой строке, скобки условий на строке условия, короткие условия/циклы/функции раскрываются на несколько строк. Лимит — 100 символов; длинные строковые данные остаются целыми. Пространства имён не добавляют уровень отступа. Сортировка include и преобразование управляющих конструкций отключены: форматтер меняет оформление, а не логику.

Используются clang-format **23.1.5** (проверяется линия 23), Prettier **3.10.1** из отдельного lock-файла и Doxygen **1.18.0**. Для веб-кода закреплены два пробела, одинарные кавычки JS и лимит 100 символов; HTML сохраняет значимые пробелы. Общие настройки редактора находятся в [`.editorconfig`](../../.editorconfig).

Однократная установка инструментов на macOS:

```sh
brew install clang-format doxygen
npm ci --prefix tools/firmware/code-style --ignore-scripts --no-audit --no-fund
python3 -m venv "$HOME/esp/tools/fcplcn-code-style"
"$HOME/esp/tools/fcplcn-code-style/bin/python" -m pip install -r tools/firmware/code-style/requirements.txt
```

Из корня проекта:

```sh
tools/firmware/format-code          # Применить стиль к собственным исходникам.
tools/firmware/format-code --check  # Проверить стиль без изменения файлов.
tools/firmware/check-doxygen        # Проверить контракты всех функций в production .cpp.
tools/firmware/docs-base            # Проверить полноту, собрать HTML API и проверить Doxygen.
```

Форматируются C++ прошивки, native-тестов и smoke-проектов, локальный веб, симулятор и его тесты. Сторонние компоненты, SDK, node_modules, CAD, бинарники и сгенерированные каталоги исключены из списка. Полное форматирование C++ отдельно проверено сравнением токенов Clang, веб-кода — AST/debug-проверкой Prettier и браузерными сценариями.

Каждое именованное определение функции в `firmware/base/main/**/*.cpp`, включая внутренние функции, шаблоны, методы, конструкторы и деструкторы, имеет собственный соседний Doxygen-блок: `@brief`, `@param` для именованных аргументов, `@return` для результата. При необходимости добавляются `@pre`, `@note` и `@details`. Документация объясняет владение JSON/буферами, единицы времени, порядок блокировок, подтверждение NVS и правила восстановления. JS использует аналогичные JSDoc-блоки для редактора и читателя.

`check-doxygen` независимо разбирает C++ с помощью закреплённых tree-sitter **0.25.2** и tree-sitter-cpp **0.23.4**. Проверяются определения всех веток препроцессора, в том числе `static` и анонимные пространства имён; наличие документации только в заголовке не заменяет комментарий в `.cpp`. Безымянные лямбды, объявления без реализации, сторонний код, тесты и сгенерированные файлы в этот подсчёт не входят. Отчёт можно сохранить через `--json /tmp/fcplcn-doxygen.json`. Окружение установлено в `~/esp/tools/fcplcn-code-style/`; другой Python задаётся `FCPLCN_CODE_STYLE_PYTHON`.

[Doxyfile](../../firmware/base/Doxyfile) собирает C++ API и исходники в `~/esp/build/fcplcn/docs/html/index.html`; другой каталог задаётся `FCPLCN_DOCS_DIR`. Имя продукта берётся из `config/product.json`. `docs-base` сначала проверяет полноту комментариев во всех production `.cpp`, затем завершается ошибкой при предупреждениях Doxygen. Генератор сохраняет публичный API и Source Browser; исключение внутренних символов из API-страниц не ослабляет отдельную проверку покрытия. HTML формируется без Graphviz и LaTeX, документация JavaScript в этот C++-справочник не включается.
